# 아라아띠 게임 구조 규칙

본 문서는 게임의 전체 흐름과 팀원 간 작업 규격을 정의합니다.

`CONVENTION.md`가 **"파일을 어디에 두는가"**에 대한 규칙이라면,
본 문서는 **"각자 만든 것을 어떻게 이어붙이는가"**에 대한 규칙입니다.

작업을 시작하기 전에 본인 담당 부분의 규격을 확인합니다.

---

## 1. 게임 전체 흐름

```text
게임 실행
   │
   ▼
┌──────────────┐
│    Boot      │  초기화 전용. 화면에는 로고만 표시되고 바로 넘어간다.
└──────────────┘
   │
   ▼
┌──────────────┐
│    Title     │  시작 메뉴. [시작] / [설정]
└──────────────┘
   │
   ▼
┌──────────────┐
│    Login     │  이메일 / 비밀번호. 인증은 하지 않는다. (11장 참고)
└──────────────┘
   │
   ▼
┌──────────────┐
│CharacterCreate│ 외형을 고르고 **캐릭터 이름**을 정한다.
└──────────────┘  이 이름이 게임에서 쓰는 유일한 이름이다. (6장 참고)
   │
   ▼
┌──────────────┐
│ChannelSelect │  서버(채널) 목록에서 하나 선택 + [입장]
└──────────────┘
   │
   │  ← 여기서 네트워크 연결이 성립한다
   ▼
┌──────────────┐
│    Lobby     │  모두가 같은 바다에 모인다. (목표 50~100명)
└──────────────┘  돌아다니다가 미니게임 입구에서 대기열에 등록한다.
   │
   │  ← 입구에서 [참가] → 4명이 모이면
   ▼
┌──────────────┐
│  MiniGame    │  무쌍 / 배 협동 / 광산
└──────────────┘
   │
   │  ← 끝나면 결과를 들고
   ▼
   Lobby 복귀
```

### 용어 정리 — "로비"의 두 가지 뜻

네트워크 쪽에서 쓰는 Lobby와 우리 게임의 로비는 **다른 것**입니다. 헷갈리지 않도록 정리합니다.

| 무엇 | 우리 프로젝트에서 | 어디에 있나 |
| --- | --- | --- |
| 서버를 고르고 접속하는 **메뉴 화면** | **`ChannelSelect`** | `ChannelSelect.unity` |
| 플레이어들이 모여 있는 **3D 허브 공간** | **`Lobby`** | `Lobby.unity` |

접속 메뉴는 별도 씬입니다. 초기 기획에서는 씬을 줄이려고 `Title` 안에서 처리하기로 했으나,
로그인과 캐릭터 생성이 중간에 들어오면서 화면을 분리했습니다.

**`Lobby`는 게임의 허브 공간입니다.** 플레이어들이 자유롭게 돌아다니다가
미니게임 입구에서 대기열에 등록하는 곳입니다.

---

## 2. 네트워크 방식 — 담당: 서버

멀티플레이 연결은 **서버 담당자**가 맡습니다.

라이브러리 선택, 서버 형태, 동기화 방식은 **서버 담당자가 결정**합니다.
클라이언트는 아래 4장에 정의된 **경계(인터페이스)를 통해서만** 네트워크와 통신합니다.

### 확정 사항

| 항목 | 결정 |
| --- | --- |
| `Lobby` 동시 접속 | **설계 목표 50~100명** / **시연 실제 10명 이하** |
| `MiniGame` 인원 | **기본 4명. 게임별로 정하며 그 게임의 규격 문서에 명시** (8장) |
| 미니게임 진입 방식 | **매칭 대기열** (아래 참고) |
| 접속 형태 | 각자 자기 컴퓨터에서 접속 |
| 클라이언트가 네트워크 코드를 직접 호출 | **금지** (4장의 경계를 통해서만) |

### 규모에 대한 판단

`Lobby`에 50~100명은 **설계 목표**이고, 실제 시연에서는 10명 이하가 접속합니다.

**따라서 개발 목표는 "동시 10~20명이 안정적으로 동작"으로 잡습니다.**
50~100명 규모의 부하 테스트는 핵심 기능이 완성된 뒤에 여유가 있으면 진행합니다.

### 권장 사항 (서버 담당자가 판단하여 변경 가능)

| 항목 | 권장 | 이유 |
| --- | --- | --- |
| 라이브러리 | Netcode for GameObjects (NGO) | Unity 공식. Unity 6.5와 호환 문제 없음 |
| 개발 초기 | **호스트 모드로 빠르게 검증** | 서버를 배포하지 않고 바로 테스트 가능 |
| 이후 | **Dedicated Server로 전환** | 50~100명 목표라면 결국 필요함 |
| 미니게임 | 로비와 **별도 세션(인스턴스)**으로 분리 | 4명이 미니게임에 있는 동안 나머지는 로비에 남아야 함 |

> **개발은 호스트 모드로, 배포는 Dedicated Server로.**
>
> NGO에서는 이 둘이 **시작 방식만 다르고 코드는 같습니다.**
> 초기에 호스트 모드로 빠르게 접속을 성공시킨 뒤 전환하면,
> 서버를 배포하느라 첫 접속이 늦어지는 일을 피할 수 있습니다.
>
> 4장의 경계만 지키면 어느 쪽이든 **클라이언트 코드는 고치지 않아도 됩니다.**

### 주의 — 시연 환경 확인 필요

교육장 공용 와이파이는 **같은 와이파이에 있어도 컴퓨터끼리 직접 통신이 막혀 있는 경우**가 있습니다.

시연 전에 반드시 실제 환경에서 여러 대(최소 4대) 동시 접속을 테스트합니다.

막혀 있다면 다음 중 하나로 해결합니다.

- 공유기를 직접 하나 가져와서 연결
- 노트북 한 대의 핫스팟에 나머지가 접속
- 인터넷 중계 서비스(Relay)를 추가로 붙임

또한 Unity 빌드를 처음 실행할 때 **Windows 방화벽 창**이 뜹니다.
반드시 **[액세스 허용] + "개인 네트워크" 체크**를 해야 합니다. 멀티플레이가 안 될 때 원인 1순위입니다.

## 3. 씬 목록과 담당자

씬 이름은 아래로 확정합니다. **임의로 변경하지 않습니다.**

```text
Assets/Game/Scenes/Main/
├── CoreGames/
│   ├── Boot.unity            (민화)
│   ├── Title.unity           (민화)
│   ├── Login.unity           (민화)
│   ├── CharacterCreate.unity (민화)   ← 씬은 민화, 안에 올리는 프리팹은 서연
│   ├── ChannelSelect.unity   (민화)
│   └── Lobby.unity           (효진)   ← 허브 공간. 미니게임 입구
└── MiniGames/
    ├── Warriors.unity    (서연)  무쌍
    ├── ShipCoop.unity    (민화)  배 협동
    └── Mine.unity        (효진)  광산
```

### 씬 규칙

- 새 씬을 만들면 반드시 `File > Build Settings`에 등록합니다. 등록하지 않으면 씬 전환이 되지 않습니다.
- **씬 전환 코드는 민화가 관리합니다.** 각자 씬에서 `SceneManager.LoadScene`을 직접 호출하지 않습니다.
- 담당하지 않은 씬은 열어보는 것은 괜찮지만 저장하지 않습니다.

## 4. 클라이언트 ↔ 서버 경계

**이 장이 본 문서에서 가장 중요합니다.**

클라이언트(민화)와 서버 담당자가 **동시에, 서로를 기다리지 않고** 작업하려면
둘 사이에 주고받을 내용을 먼저 고정해야 합니다.

### 원칙

```text
클라이언트(화면)              경계                  서버(네트워크)
─────────────────      ─────────────────      ─────────────────
버튼을 누르면          →   요청을 보낸다   →     실제 접속 처리
화면에 표시한다        ←   알림을 받는다   ←     결과를 알려준다
```

- 클라이언트는 **네트워크 라이브러리 함수를 직접 부르지 않습니다.**
- 서버 담당자는 **화면(UI)을 직접 건드리지 않습니다.**
- 서로 이 경계를 통해서만 대화합니다.

이렇게 하면 서버 담당자가 나중에 라이브러리를 바꾸거나 Dedicated Server로 옮겨도
**클라이언트 코드는 한 줄도 고치지 않아도 됩니다.**

### 방은 없습니다. 서버(채널)를 고릅니다

플레이어가 방을 만들거나 고르지 않습니다.
대신 **미리 준비된 서버 목록에서 하나를 골라** 접속합니다.

```text
ChannelSelect   서버 목록에서 하나 선택 → [입장]

                  서버 1   (12 / 100)
                  서버 2   ( 3 / 100)      ← 이런 목록
   ↓
Lobby    고른 서버의 로비에 들어간다
   ↓
         미니게임 입구에서 [참가] → 4명 모이면 자동 입장
```

서버 목록은 **서버 담당자가 정합니다.**

처음에는 서버 1개로 시작하고, 나중에 서버를 늘리면 목록에 항목이 추가됩니다.
**서버를 늘려도 클라이언트 코드는 고치지 않아도 됩니다.** 목록을 그대로 화면에 뿌리기 때문입니다.

### 클라이언트가 서버에게 요청하는 것

| 요청 | 언제 | 함께 보내는 것 |
| --- | --- | --- |
| 서버 목록 요청 | ChannelSelect 화면에 들어왔을 때, [새로고침] 클릭 | — |
| 로비 접속 | 서버를 고르고 [입장] 클릭 | **캐릭터 이름**, **서버 ID** |
| 미니게임 대기열 등록 | 로비에서 미니게임 [참가] 클릭 | 미니게임 이름 |
| 대기 취소 | [취소] 클릭 | — |
| 미니게임 결과 보고 | 미니게임이 끝났을 때 | 성공 여부, 점수 |
| 접속 종료 | [나가기] 클릭 | — |

### 서버가 클라이언트에게 알려주는 것

| 알림 | 언제 | 함께 주는 것 |
| --- | --- | --- |
| **서버 목록** | 목록 요청에 대한 응답 | 서버별 이름 / 현재 인원 / 최대 인원 |
| 접속 결과 | 접속 시도 후 | 성공 여부, **실패했다면 그 이유** |
| 로비 인원 변경 | 누가 들어오거나 나갈 때 | 현재 로비 인원 수 |
| 대기 인원 갱신 | 대기열 인원이 바뀔 때 | 미니게임 이름, 현재 인원, 필요 인원 |
| **매칭 완료** | 4명이 모였을 때 | 어느 미니게임으로 갈지 |
| 연결 끊김 | 접속이 끊겼을 때 | 끊긴 이유 |

### 코드 형태 (서버 담당자가 구현)

```csharp
// Assets/Game/Scripts/Network/INetworkService.cs
// 서버 담당자가 이 형태로 만들고, 클라이언트는 이것만 사용한다.

// 서버 하나의 정보
public struct ServerInfo
{
    public string Id;             // 내부 식별용
    public string DisplayName;    // 화면에 보일 이름 ("서버 1")
    public int CurrentPlayers;    // 현재 접속 인원
    public int MaxPlayers;        // 최대 인원
}

public interface INetworkService
{
    // 클라이언트 → 서버
    void RequestServerList();
    void Connect(string nickname, string serverId);
    void Disconnect();
    void JoinMiniGameQueue(string miniGameName);
    void LeaveMiniGameQueue();
    void ReportMiniGameResult(bool success, int score);

    // 서버 → 클라이언트
    event Action<ServerInfo[]> OnServerListUpdated;    // 서버 목록
    event Action<bool, string> OnConnectResult;        // 성공 여부, 실패 이유
    event Action<int> OnLobbyPlayerCountChanged;       // 현재 로비 인원
    event Action<string, int, int> OnQueueUpdated;     // 미니게임명, 현재 인원, 필요 인원(4)
    event Action<string> OnMiniGameStarting;           // 매칭 완료. 이 미니게임으로 이동
    event Action<string> OnDisconnected;               // 끊긴 이유
}
```

세부 사항은 두 담당자가 상의해서 조정할 수 있습니다.
**다만 조정한 내용은 반드시 이 문서에 반영합니다.**

### 계정 · 캐릭터는 별도 경계입니다

로그인과 캐릭터 저장은 `INetworkService` 에 **넣지 않습니다.** 따로 둡니다.

```text
Assets/Game/Scripts/Account/
├── IAuthService.cs        회원가입 · 로그인 · 현재 로그인 상태
├── ICharacterService.cs   내 캐릭터 목록 · 캐릭터 생성
└── AccountServiceLocator  둘을 담아두는 곳 (NetworkServiceLocator 와 같은 방식)
```

나눈 이유

1. `INetworkService` 는 Photon Fusion 기반 **실시간 세션**이고,
   계정 · 캐릭터는 **단발성 요청/응답**입니다. 성격이 다릅니다.
   그래서 `Network/` 아래가 아니라 **별도 폴더**에 둡니다.
2. 가짜 ↔ 진짜를 **각각 따로** 갈아끼울 수 있어야 합니다.
   (서버 인증은 붙었는데 채널은 아직 가짜인 중간 상태가 실제로 생깁니다)

`INetworkService` 와 마찬가지로 **혼자 고치지 않고 함께 정합니다.**

가짜에서 진짜로 바꾸는 지점은 `AccountServiceBootstrap` 파일 한 곳입니다.
씬을 고치지 않습니다.

캐릭터는 **언제나 목록(배열)으로** 주고받습니다. 지금은 계정당 1개지만,
나중에 다중 캐릭터를 붙일 때 경계를 고치지 않기 위해서입니다.

### 씬 전환은 클라이언트가 합니다

서버는 **"지금 이동할 시점이다"**라고 알려주기만 하고,
실제로 씬을 넘기는 것은 클라이언트가 합니다.

```text
4명이 대기열에 모임
        ↓
서버: OnMiniGameStarting("ShipCoop") 을 그 4명에게만 보냄
        ↓
그 4명의 클라이언트: 각자 ShipCoop 씬으로 이동
        ↓
로비에 남은 나머지 사람들은 그대로 로비에 있음
```

### 서버가 아직 준비되지 않았을 때

**클라이언트는 서버 담당자를 기다리지 않습니다.**

`INetworkService`를 **항상 성공하는 가짜 구현**으로 하나 만들어두면,
네트워크 없이도 Title 화면과 씬 전환을 전부 완성하고 테스트할 수 있습니다.

```text
FakeNetworkService     ← 민화가 만든 가짜. 버튼 누르면 무조건 성공 처리
        ↓
        ↓ 나중에 갈아끼움
        ↓
RealNetworkService     ← 서버 담당자가 만든 진짜
```

화면 코드는 둘 중 무엇이 꽂혀 있는지 몰라도 됩니다. **그래서 고칠 필요가 없습니다.**

## 5. 캐릭터 프리팹 규격 — 담당: 서연

### 위치

```text
Assets/Game/Prefabs/Characters/Player.prefab
```

### 반드시 지켜야 할 것

**1) 씬에 캐릭터를 미리 배치하지 않습니다.**

멀티플레이에서 캐릭터는 플레이어가 접속하는 순간 생성됩니다.
씬에 미리 놓아둔 캐릭터는 사용되지 않습니다.

**2) 프리팹의 맨 위 오브젝트는 빈 오브젝트로 만듭니다.**

```text
Player               ← 빈 오브젝트 (여기에 스크립트가 붙습니다)
├── Model            ← 실제 캐릭터 모델
│   └── (본, 파츠 등)
└── (기타)
```

모델을 바로 맨 위에 두면 나중에 스크립트를 붙일 때 회전 축이 어긋납니다.

**3) 이동 스크립트와 네트워크 스크립트는 넣지 않습니다.**

서연이 담당하는 것은 **모델, 애니메이션, 프리팹 구조**까지입니다.

이동 스크립트는 클라이언트가, 네트워크 관련 컴포넌트는 서버 담당자가 붙입니다.

**4) 애니메이터 파라미터 이름을 아래로 맞춥니다.**

| 이름 | 타입 | 뜻 |
| --- | --- | --- |
| `Speed` | Float | 이동 속도. 0이면 정지, 클수록 빠르게 |
| `IsGrounded` | Bool | 땅에 닿아 있는지 |

코드에서 이 이름으로 값을 넣습니다. 이름이 다르면 애니메이션이 동작하지 않습니다.

필요한 파라미터가 더 생기면 상의 후 이 표에 추가합니다.

## 6. 캐릭터 생성 화면 규격 — 담당: 서연

`CharacterCreate` 씬에서 **외형을 고르고 캐릭터 이름을 정합니다.**

이 화면에서 정한 이름이 **게임에서 쓰는 유일한 이름**입니다.
사용자 닉네임은 따로 두지 않습니다. `Login` 화면의 이메일은 이름으로 쓰지 않습니다.

### 위치

```text
Assets/Game/Prefabs/Characters/CharacterCustomization.prefab
```

UI 는 프리팹으로 만듭니다. `Scenes/Develop/서연/` 의 테스트 씬은 이 프리팹을 올려두고
테스트하는 용도이며, 씬 안에 UI 를 직접 만들지 않습니다.
프리팹이 없으면 `CharacterCreate` 씬에 배치할 수 없습니다. (`CONVENTION.md` 2장)

### 이름을 넘기는 방법 — PlayerPrefs

> **⚠ 2026-09-09 갱신: 원본은 서버입니다.**
>
> 캐릭터가 있는지 · 이름이 무엇인지 · 외형이 어떤지는 모두 **서버(MySQL)가 정합니다.**
> 로그인 후 어느 화면으로 갈지도 `GET /api/characters` 결과로 판단합니다.
>
> 아래 `PlayerPrefs` 두 키는 이제 **그 응답의 캐시**입니다. 두 가지 목적으로만 남겨 둡니다.
>   1. 기존 UI 호환 — `SceneFlow.Nickname` 과 `ChannelSelectController` 가 이 키를 읽습니다.
>   2. 로그인 없이 `CharacterCreate` 씬만 단독 실행할 때의 외형 복원
>
> **서버 응답이 오면 언제나 서버 값이 이깁니다.** 캐시를 근거로 분기하지 않습니다.
> 갱신하는 곳은 `Assets/Game/Scripts/Account/CharacterSessionCache.cs` 한 곳입니다.
> 자세한 내용은 `docs/prd/auth-character-roadmap.md` PRD 07 을 봅니다.

캐릭터 이름과 외형은 `PlayerPrefs` 에도 함께 남습니다. (위 캐시 목적)

| 키 | 타입 | 내용 |
| --- | --- | --- |
| `PlayerNickname` | string | 캐릭터 이름. **키 이름을 바꾸지 않습니다.** |
| `Char.*` | int / string | 외형. 파츠별 `int` 또는 JSON 문자열 하나 |

`[생성 완료]` 를 누를 때 저장합니다.

```csharp
PlayerPrefs.SetString("PlayerNickname", nameInput.text.Trim());
PlayerPrefs.Save();
```

`ChannelSelect` 가 이 키를 읽어 서버에 넘깁니다. **키 이름이 정확히 맞아야** 연결됩니다.

```csharp
// ChannelSelectController — 이미 이렇게 읽고 있습니다
PlayerPrefs.GetString("PlayerNickname", string.Empty)
```

### 반드시 지켜야 할 것

**1) 빈 이름으로 넘어가지 못하게 막습니다.**

서버는 빈 이름을 접속 실패로 처리합니다. 막지 않으면 `ChannelSelect` 까지 갔다가
입장에서 "닉네임을 입력해 주세요" 가 뜨는데, 사용자는 어디서 입력해야 하는지 알 수 없습니다.

**2) 씬 전환 코드를 넣지 않습니다.**

`[생성 완료]` 는 **저장만** 합니다. 다음 화면으로 넘기는 것은 클라이언트가 붙입니다.
(3장 씬 규칙 — 씬 전환 코드는 민화가 관리)

### 두 번째 실행부터

`PlayerNickname` 이 이미 있으면 `CharacterCreate` 를 건너뛰고 `ChannelSelect` 로 바로 갑니다.
이 판단은 씬 전환이므로 **클라이언트(민화)** 가 합니다.

## 7. Lobby 씬 규격 — 담당: 효진

`Lobby`는 플레이어들이 모여 미니게임 대기열에 등록하는 **허브 공간**입니다.

### 반드시 포함해야 할 것

**1) 플레이어 시작 위치 — 방식은 추후 확정**

스폰 지점 오브젝트(`SpawnPoint_01`, `SpawnPoint_02` …)는 **만들지 않습니다.**

로비에 여러 명이 동시에 들어올 때 캐릭터를 어디에 생성할지는 아직 정하지 않았습니다.
클라이언트와 서버 담당자가 상의해서 정하고, **정해지면 본 문서에 반영합니다.**

그때까지 로비에서 보장해야 할 것은 아래 3) 의 **캐릭터가 서도 되는 넓고 평평한 바닥**뿐입니다.
어디를 스폰 영역으로 쓸지는 방식이 정해진 뒤에 고릅니다.

**2) 미니게임 입구 3개**

```text
Hierarchy
└── Entrances
    ├── Entrance_Warriors    ← 무쌍
    ├── Entrance_ShipCoop    ← 배 협동
    └── Entrance_Mine        ← 광산
```

각 입구 오브젝트에는 **Collider를 붙이고 `Is Trigger`를 체크**합니다.

캐릭터가 이 영역에 들어오면 **[참가] 버튼이 뜨고, 누르면 대기열에 등록**됩니다.
들어가자마자 미니게임이 시작되는 것이 아닙니다. **정원이 모여야 시작됩니다.**

정원은 게임별로 다릅니다 (8장). **인원이 가변인 게임은 정원이 차기 전에도 시작할 수
있으므로, 대기 UI 에 [지금 시작] 을 함께 둡니다.**

입구 근처에 **대기 인원을 표시할 자리**(예: 간판, 안내판)를 하나 두면 좋습니다.
`2 / 4 대기 중` 같은 표시가 여기에 들어갑니다.

보기 좋게 문이나 표지판 모델을 붙이는 것은 자유입니다.

**3) 바닥에 Collider**

바닥에 Collider가 없으면 캐릭터가 아래로 떨어집니다.

### 하지 않아야 할 것

- 씬에 캐릭터를 배치하지 않습니다 (접속할 때 생성됨)
- `Entrance_*` 이름을 규격과 다르게 짓지 않습니다 (코드가 이 이름으로 찾습니다)

### 자유롭게 해도 되는 것

조명, 지형, 물, 후처리, 장식물, 스카이박스 등 보이는 것은 모두 자유입니다.

## 8. 미니게임 규격

### 현재 상태 — 추후 확정

미니게임의 상세 규격은 **Lobby가 완성된 이후에 확정**합니다.

**그전까지 미니게임 제작을 시작하지 않습니다.**
규격 없이 각자 만들면 나중에 합칠 때 전부 다시 만들어야 합니다.

### 지금 확정된 것 (이것만 지키면 됩니다)

**1) 인원은 게임별로 정합니다.**

기본은 **4명**입니다. 다만 게임 성격상 다른 인원이 자연스러우면 다르게 둘 수 있고,
**그 게임의 규격 문서에 반드시 명시**합니다. 문서에 없으면 4명 고정입니다.

| 게임 | 인원 | 근거 |
| --- | --- | --- |
| 무쌍 (Warriors) | 4명 고정 | 담당자가 규격 문서에서 확정 |
| 배 협동 (ShipCoop) | **4명 고정** | 배 HP 공유와 작업 5종 배분이 4명을 전제로 설계됨 (`SHIPCOOP.md`) |
| 광산 (Mine) | **1~4명** | 인원이 곧 난이도. 적으면 쉬운 그림, 많으면 복잡한 그림 (`MINE.md`) |

인원을 몇 명으로 정하든 **그 인원으로 재미있게 동작하면 됩니다.** 모든 인원수를 지원할
필요는 없습니다.

> **인원이 가변인 게임은 대기열이 다 차기 전에도 시작할 수 있어야 합니다.**
> 대기 UI 에 **[지금 시작]** 을 두고, 누르면 현재 모인 인원으로 시작합니다.
> 현재 4장의 경계에는 대기열 등록·해제만 있으므로 이 요청을 추가합니다. (민화 · 건희 합의 완료)

**2) 끝날 때 아래 두 가지를 반드시 돌려줍니다.**

```text
성공 / 실패     (예 / 아니오)
점수            (숫자)
```

미니게임을 어떻게 만들든 이 두 가지만 나오면 Lobby에 연결할 수 있습니다.

## 9. 스크립트 폴더 구조

```text
Assets/Game/Scripts/
├── Core/             씬 전환, 게임 상태 관리        (민화)
├── Account/          계정 인증, 캐릭터 저장 경계    (서버 — 4장)
├── Network/          접속, 매칭, 동기화             (서버)
├── IoT/              IoT 컨트롤러 경계              (공용 — 아래 참고)
├── Character/        캐릭터 커스터마이징            (서연)
│                     캐릭터 이동, 애니메이션 연결   (민화)
├── UI/               화면 버튼 처리                 (민화)
└── MiniGames/
    ├── Warriors/                                    (서연)
    ├── ShipCoop/                                    (민화)
    └── Mine/                                        (효진)
```

본인 담당 폴더 밖의 스크립트는 수정하지 않습니다.
수정이 필요하면 담당자에게 요청합니다.

**단, 아래 두 곳은 예외입니다. 여러 명이 함께 정합니다.**

| 폴더 | 파일 | 함께 정하는 사람 |
| --- | --- | --- |
| `Network/` | `INetworkService` | 클라이언트 ↔ 서버 (4장) |
| `Account/` | `IAuthService` · `ICharacterService` | 클라이언트 ↔ 서버 (4장) |
| `IoT/` | `IPlayerController` | 미니게임 담당 3명 ↔ IoT 담당 (아래) |

### `IoT/` 는 세 명이 함께 쓰는 폴더입니다

**미니게임 세 개가 같은 IoT 컨트롤러 하나를 씁니다.**
같은 센서(IMU · 압력센서 · 버튼 · 진동 모터 · LED)를 게임 상황에 따라 다르게 쓸 뿐,
플레이어가 손에 쥐는 장치는 하나입니다.

그래서 컨트롤러 인터페이스는 특정 미니게임의 것이 아니라 **공용 경계**입니다.

```text
Assets/Game/Scripts/IoT/
├── IPlayerController.cs         ← 공용 경계. 함께 정한다
├── KeyboardPlayerController.cs  ← 장치 없이 키보드로 테스트하는 가짜 구현
└── IotPlayerController.cs       ← 진짜 장치. IoT 담당자가 만든다
```

```csharp
// 컨트롤러 1대 = 플레이어 1명
public interface IPlayerController
{
    // 입력 (장치 → 게임)
    float Tilt      { get; }   // IMU 기울기  -1 ~ +1
    float Rotation  { get; }   // IMU 회전    -1 ~ +1
    bool  Button    { get; }   // 물리 버튼 (누르고 있는지)
    bool  Grip      { get; }   // 압력센서 HOLD 판정
    bool  ConsumeButtonPress();// 버튼이 새로 눌렸는지 1회
    bool  ConsumeSwing();      // IMU 제스처(휘두르기) 1회

    // 출력 (게임 → 장치)
    void Vibrate(float strength, float seconds);   // 진동 모터
    void SetLed(Color color);                      // LED
}
```

**규칙**

1. **자기 미니게임 폴더 안에 컨트롤러 인터페이스를 따로 만들지 않습니다.**
   세 벌이 생기면 IoT 담당자가 같은 것을 세 번 구현해야 합니다.
2. **이 파일을 고쳐야 하면 혼자 고치지 않고 먼저 팀에 알립니다.**
   세 미니게임이 전부 이 파일을 참조하므로, 한 명이 바꾸면 나머지 둘의 코드가 깨집니다.
3. 조정한 내용은 **반드시 이 문서에 반영합니다.**

### 장치를 기다리지 않습니다

`FakeNetworkService`와 같은 방식입니다. (4장 참고)

```text
KeyboardPlayerController   ← 키보드로 전부 테스트할 수 있다
        ↓
        ↓ 나중에 갈아끼움
        ↓
IotPlayerController        ← IoT 담당자가 만든 진짜 장치
```

게임 로직은 둘 중 무엇이 꽂혀 있는지 몰라도 됩니다. **그래서 고칠 필요가 없습니다.**

> 센서를 게임 행동에 어떻게 연결하는지(조타 = IMU 회전, 수리 = 망치질 동작 등)는
> 미니게임마다 다릅니다. 배 협동 게임의 매핑은 `SHIPCOOP.md` 7장을 참고하세요.

```bash
git config --get-regexp "^filter\.lfs"
```

아무것도 안 나오면 `git lfs install`을 한 번 실행합니다.

### Import 후 확인

```bash
git status
```

의도하지 않은 파일이 포함되지 않았는지 확인합니다.

## 11. 이번 프로젝트에서 하지 않는 것

초기 기획안(`README.md`)에는 아래 내용이 있으나, 남은 기간을 고려하여 **우선순위에서 제외**합니다.

| 기획안 내용 | 실제 진행 방식 |
| --- | --- |
| 50~100명 실제 부하 감당 | **개발 목표는 10~20명.** 그 이상은 여유가 있으면 검토 |
| Docker / Kubernetes | 핵심 기능 완성 후 여유가 있으면 검토 |
| Prometheus / Grafana 모니터링 | 핵심 기능 완성 후 여유가 있으면 검토 |
| 로그인 / 회원가입 | ~~제외~~ → **도입합니다.** `server/` 의 ASP.NET Core API 가 계정을 저장하고 JWT 로 인증합니다. `Login` 씬 연동은 아직 남아 있습니다 (`docs/prd/auth-character-roadmap.md` PRD 06) |
| 사용자 닉네임 | **없습니다.** 이름은 `CharacterCreate` 에서 정하는 **캐릭터 이름 하나**뿐입니다 (6장) |
| 캐릭터를 서버에 저장 | ~~제외~~ → **도입합니다.** DB 스키마(`users` · `characters` · `character_parts`)는 준비됐고, 지금은 `PlayerPrefs` 로 그 PC 에만 저장합니다. 서버 저장 API 와 Unity 연동이 남아 있습니다 (같은 문서 PRD 05 · 07) |
| 플레이어가 방을 만들고 고르는 기능 | **없음.** 서버(채널)를 고르면 그 서버의 로비로 들어감 |

> **위 표의 로그인 / 회원가입 · 캐릭터 서버 저장 두 줄은 방향이 바뀌었습니다.**
> 계정과 캐릭터를 실제로 저장하기로 팀에서 정했고, 단계별 계획은
> `docs/prd/auth-character-roadmap.md` 에 있습니다.
> 2026-09-09 기준 서버 쪽 회원가입 · 로그인 API 와 JWT 까지 완료됐습니다.
> **Unity 쪽은 아직 붙지 않았습니다.** `Login` 씬은 여전히 검증 없이 통과시킵니다.

### 범위에 포함되는 것

아래는 로비 규모 때문에 **반드시 필요**합니다. 제외 대상이 아닙니다.

- **Dedicated Server** — 로비를 여러 명이 상시 사용하려면 필요합니다
- **미니게임 인스턴스 분리** — 4명이 미니게임에 있는 동안 나머지는 로비에 남아야 합니다

다만 개발 초기에는 호스트 모드로 빠르게 검증한 뒤 전환하기를 권합니다. (2장 참고)

## 12. 진행 순서

### 지금은 두 갈래가 동시에 진행됩니다

```text
[서버 담당자]                          [민화]
─────────────────────────             ─────────────────────────
1. 큐브 하나가 두 창에서                1. Boot → Title 씬과
   서로 보이고 움직인다                    씬 전환을 만든다
        ↓                                      ↓
2. 여러 명 동시 접속 확인               2. 채널 선택 화면과
                                           미니게임 대기 UI를 만든다
        ↓                                      ↓
3. INetworkService 구현                 3. FakeNetworkService(가짜)로
                                           화면 흐름을 완성한다
        └──────────────┬───────────────────────┘
                       ↓
              4. 가짜를 진짜로 갈아끼운다
                       ↓
              5. 큐브를 서연의 캐릭터로 교체
                       ↓
              6. 빈 바닥을 효진의 맵으로 교체
                       ↓
              7. 미니게임 규격 확정        (전체 회의)
                       ↓
              8. 각자 미니게임 제작        (전체)
                       ↓
              9. IoT 장치 연결             (전체)
```

### 중요

**아무도 서로를 기다리지 않습니다.**

- 민화는 가짜 네트워크로 화면을 완성합니다.
- 서버 담당자는 큐브로 접속을 완성합니다.
- 민화는 캐릭터와 맵이 나오기 전에 큐브와 빈 바닥으로 먼저 만듭니다.

**4장의 경계를 먼저 합의해두는 것이 이 방식의 전제입니다.**
경계가 없으면 서로 기다리게 되고, 나중에 합칠 때 전부 뜯어야 합니다.

# 핵심 규칙 요약

1. 씬 이름은 본 문서의 목록으로 고정합니다.
2. **클라이언트는 네트워크 코드를 직접 부르지 않습니다.** 4장의 경계를 통해서만 대화합니다.
3. 네트워크 구현 방식은 **서버 담당자가 결정**합니다. 경계만 지키면 됩니다.
4. 캐릭터는 씬에 미리 배치하지 않습니다. 접속할 때 생성됩니다.
5. 캐릭터 프리팹의 맨 위는 빈 오브젝트로 만들고, 애니메이터 파라미터는 `Speed`, `IsGrounded`로 맞춥니다.
6. Lobby에는 `Entrance_*` 3개를 규격대로 배치합니다. 스폰 방식은 추후 확정입니다.
7. 미니게임 인원은 **게임별로 정하고 규격 문서에 명시**합니다(기본 4명). **매칭 대기열**로
   입장하며, 끝날 때 성공/실패와 점수를 돌려줍니다.
8. 미니게임 제작은 규격이 확정되기 전까지 시작하지 않습니다.
9. 씬 전환은 민화가 관리합니다. 각자 씬에서 직접 호출하지 않습니다.
10. 에셋을 Import 하기 전에 팀에 먼저 공유합니다.
11. **서로를 기다리지 않습니다.** 가짜 구현과 임시 오브젝트로 각자 끝까지 만든 뒤 갈아끼웁니다.
